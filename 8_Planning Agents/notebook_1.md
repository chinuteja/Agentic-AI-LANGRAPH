# 📝 Agentic AI Blog Writer with LangGraph

A beginner-friendly example of building an **Agentic AI Blog Writer using LangGraph**.

The application takes a topic, creates a structured blog plan, sends each planned section to a worker, combines the generated sections, and produces a final Markdown blog.

The main LangGraph concept demonstrated here is **Fan-Out / Fan-In using `Send`**.

---

## 🧠 What Are We Building?

Suppose we give the application this topic:

```text
The Future of Artificial Intelligence in Everyday Life
```

The application first creates a plan:

```text
Blog Title:
The Future of Artificial Intelligence in Everyday Life

Tasks:
1. Introduction
2. AI in Healthcare
3. AI in Education
4. AI in Workplaces
5. AI in Smart Homes
6. Benefits and Risks
7. Future of AI
```

Instead of asking one LLM call to write the entire blog, each task is sent to a worker.

The overall workflow is:

```text
                    Topic
                      │
                      ▼
                Orchestrator
                      │
                      ▼
                  Blog Plan
                      │
                      ▼
                    Fanout
              ┌───────┼───────┐
              ▼       ▼       ▼
           Worker  Worker  Worker  ...
              │       │       │
              └───────┼───────┘
                      ▼
                   Reducer
                      │
                      ▼
                 Final Blog
                      │
                      ▼
                     END
```

This pattern is called:

```text
Fan-Out → Workers → Fan-In
```

# 1️⃣ State

The graph uses a state similar to:

```python
class State(TypedDict):

    plan: Plan

    topic: str

    sections: Annotated[
        List[str],
        operator.add
    ]

    final: str
```

Think of the state as the **shared memory of the graph**.

It contains:

```text
State
│
├── topic
├── plan
├── sections
└── final
```

### `topic`

The topic provided by the user.

Example:

```text
The Future of Artificial Intelligence in Everyday Life
```

### `plan`

The structured blog plan created by the orchestrator.

### `sections`

The sections generated by the workers.

### `final`

The final blog after all sections are combined.

---

# 2️⃣ Task

A task represents one piece of work that a worker needs to complete.

The project uses a Pydantic model similar to:

```python
class Task(BaseModel):

    id: int

    title: str

    brief: str
```

For example:

```text
Task
│
├── id: 1
├── title: AI in Healthcare
└── brief: Explain how AI is changing healthcare.
```

---

# 3️⃣ Plan

The plan contains the blog title and all the tasks.

```python
class Plan(BaseModel):

    blog_title: str

    tasks: List[Task]
```

For example:

```text
Plan
│
├── blog_title
│
└── tasks
     ├── Introduction
     ├── AI in Healthcare
     ├── AI in Education
     ├── AI in Workplaces
     └── Future of AI
```

The LLM generates this plan before the workers start writing.

---

# 4️⃣ Orchestrator

The **orchestrator** creates the blog plan.

Conceptually:

```text
User Topic
    ↓
Orchestrator
    ↓
Blog Plan
```

The orchestrator asks the LLM to create a structured `Plan`.

A simplified version looks like:

```python
def orchestrator(state: State):

    plan = llm.with_structured_output(
        Plan
    ).invoke(...)

    return {
        "plan": plan
    }
```

The important part is:

```python
llm.with_structured_output(Plan)
```

This tells the LLM to return data matching the `Plan` structure.

---

# 5️⃣ Fan-Out

This is the most important concept in this project.

The `fanout()` function takes all the tasks from the plan and sends them to the worker.

A readable version is:

```python
def fanout(state: State):

    tasks = []

    for task in state["plan"].tasks:

        task_input = {
            "task": task,
            "topic": state["topic"],
            "plan": state["plan"]
        }

        tasks.append(
            Send(
                "worker",
                task_input
            )
        )

    return tasks
```

Let's understand it.

Suppose the plan contains:

```text
Task 1 → Introduction
Task 2 → AI in Healthcare
Task 3 → AI in Education
```

The function creates:

```text
Worker → Introduction

Worker → AI in Healthcare

Worker → AI in Education
```

So one plan is split into multiple independent tasks.

That is **Fan-Out**.

---

# 6️⃣ Why `Send`?

`Send` allows LangGraph to dynamically send different inputs to the same worker node.

For example:

```python
Send(
    "worker",
    {
        "task": task,
        "topic": state["topic"],
        "plan": state["plan"]
    }
)
```

means:

> Run the `worker` node with this particular task.

If there are seven tasks, seven worker executions can be created.

```text
                  Fanout
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Worker 1     Worker 2     Worker 3
       │            │            │
       ▼            ▼            ▼
    Section 1    Section 2    Section 3
```

---

# 7️⃣ Worker

The worker receives one task.

Conceptually:

```python
def worker(payload):

    task = payload["task"]

    topic = payload["topic"]

    plan = payload["plan"]
```

The worker then asks the LLM to write that specific section.

For example:

```text
Task:
AI in Healthcare

Brief:
Explain how AI is changing healthcare.
```

The worker generates something like:

```markdown
## AI in Healthcare

Artificial intelligence is changing healthcare by...
```

The worker returns:

```python
return {
    "sections": [section_md]
}
```

---

# 8️⃣ Why Multiple Workers?

Without fan-out, we could write the blog sequentially:

```text
Write Section 1
      ↓
Write Section 2
      ↓
Write Section 3
      ↓
Write Section 4
      ↓
Write Section 5
```

With fan-out:

```text
             Blog Plan
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
    Worker     Worker     Worker
       │         │         │
    Section    Section    Section
       1          2          3
```

The sections are independent, so they can be processed separately.

This makes the workflow easier to extend and demonstrates a common multi-agent pattern.

---

# 9️⃣ Reducer

After the workers finish, the **reducer** combines their results.

Conceptually:

```python
def reducer(state: State):

    title = state["plan"].blog_title

    body = "\n\n".join(
        state["sections"]
    ).strip()

    final_md = f"# {title}\n\n{body}\n"

    return {
        "final": final_md
    }
```

Suppose workers generated:

```text
Section 1
Section 2
Section 3
```

The reducer combines them:

```markdown
# The Future of Artificial Intelligence

Section 1

Section 2

Section 3
```

This is the **Fan-In** part of the workflow.

---

# 🔟 Why `Annotated[List[str], operator.add]`?

The state contains:

```python
sections: Annotated[
    List[str],
    operator.add
]
```

This is important because multiple workers are updating the same state key.

Imagine:

```text
Worker 1 → ["Introduction"]

Worker 2 → ["AI in Healthcare"]

Worker 3 → ["AI in Education"]
```

The reducer combines them:

```text
[
    "Introduction",
    "AI in Healthcare",
    "AI in Education"
]
```

The `operator.add` reducer tells LangGraph to combine these updates rather than treating each update as a replacement.

---

# 1️⃣1️⃣ Creating the Graph

The graph is created with:

```python
graph = StateGraph(State)
```

Then the nodes are added:

```python
graph.add_node(
    "orchestrator",
    orchestrator
)

graph.add_node(
    "worker",
    worker
)

graph.add_node(
    "reducer",
    reducer
)
```

So we have three main nodes:

```text
Orchestrator
Worker
Reducer
```

---

# 1️⃣2️⃣ Connecting the Graph

First:

```python
graph.add_edge(
    START,
    "orchestrator"
)
```

This means:

```text
START
  ↓
Orchestrator
```

Then the orchestrator uses `fanout()`:

```python
graph.add_conditional_edges(
    "orchestrator",
    fanout,
    ["worker"]
)
```

This dynamically creates worker executions.

Then:

```python
graph.add_edge(
    "worker",
    "reducer"
)
```

The worker results go to the reducer.

Finally:

```python
graph.add_edge(
    "reducer",
    END
)
```

The workflow ends.

# 🧠 Beginner Mental Model

If you are completely new to LangGraph, remember this:

## State

Stores information.

```text
State = Shared Information
```

## Node

A Python function that does work.

```text
Node = Worker
```

## Edge

Connects nodes.

```text
Edge = Where should the graph go next?
```

## Conditional Edge

Makes a routing decision.

```text
Conditional Edge = Which path should we take?
```

## Send

Sends different tasks to workers.

```text
Send = Give this worker this particular task
```

## Reducer

Combines results from multiple workers.

```text
Reducer = Combine worker results
```

# 🔥 Fan-Out vs Fan-In

This project demonstrates both.

## Fan-Out

One plan becomes many tasks:

```text
             Plan
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
     Task 1  Task 2  Task 3
```

## Fan-In

Many results become one final output:

```text
     Task 1 ──┐
     Task 2 ──┤
     Task 3 ──┤
              ▼
           Reducer
              │
              ▼
          Final Blog
```

Together:

```text
Fan-Out
   ↓
Workers
   ↓
Fan-In
```

# 🎯 Why This Architecture?

A single LLM could write the entire blog in one call.

However, this architecture separates responsibilities:

```text
Orchestrator
    ↓
Plans the work

Worker
    ↓
Writes individual sections

Reducer
    ↓
Combines everything
```

This makes the workflow:

- Easier to understand
- Easier to debug
- Easier to extend
- Suitable for independent parallel tasks
- A useful foundation for multi-agent systems
